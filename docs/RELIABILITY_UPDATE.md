# 운영 예외 처리 보완 — 2026-10-12

기존 매장 데이터와 직원 계정을 유지하는 업데이트입니다. 업데이트 전 백업을 다운로드하고 서버를 종료한 뒤 `git pull`, `start.bat` 순서로 실행하세요. 기존 아이디·비밀번호는 변경하지 않습니다.

## 수납과 재고

- **수납 상세 → 금액 정정·재수납**: 같은 시술·상품의 단가와 전체 할인액을 수정합니다. 기존 단말기 결제 취소와 새 금액 결제를 실제로 처리한 뒤 취소 번호·새 승인번호·사유를 기록합니다. ERP는 기존 전액 환불과 새 수납을 한 트랜잭션으로 기록하고 예약을 새 수납에 연결합니다. 이미 사용한 재료와 상품 재고는 다시 차감하지 않습니다.
- 원 수납 금액·환불 이력은 보존합니다. 환불 이력이 있는 수납은 이 기능으로 다시 정정할 수 없으며 남은 금액 환불을 이용합니다. 이미 과거에 잘못 등록한 별도 수납은 자동으로 찾아 합치거나 재고를 역산하지 않습니다.
- **환불 기록 → 시술 항목 → 환불 기준 → 금액 직접 입력**: 50,000원 시술 중 10,000원 환불처럼 원 단위로 입력합니다. 남은 결제액을 넘을 수 없으며 수량 환불과 섞어도 누적액을 검사합니다. 판매 상품은 실제 반환 수량과 재입고 여부를 기존 방식대로 기록합니다.
- **수납 작성 → 실제 재료 사용량 조정**: 해당 시술들의 재료별 총 사용량을 수정합니다. 기본량과 다르면 사유가 필수입니다. 실제 차감량·기본량·단위·사유가 수납에 보존됩니다. 지참 재료 등으로 사용하지 않았다면 사유와 함께 0을 입력할 수 있습니다.
- 미래 예약의 방문 확인·시술 시작은 화면과 서버에서 차단합니다. 오늘 방문했다면 먼저 예약일을 오늘로 변경해야 하며, 중복 예약 검사는 그대로 적용됩니다.

## 발주와 거래처 정산

**발주 상세**에서 처리합니다. 실제 거래처 주문 전달·은행 이체는 별도로 수행합니다.

| 기능 | 결과 |
|---|---|
| 미입고 잔량 취소 | 품목별 더 이상 받지 않을 개수만 취소. 기존 입고·재고는 유지하고 미입고 잔량과 정산 금액을 감소 |
| 분할 지급·환급 → 대금 지급 | 실제 지급액을 여러 번 기록. 남은 지급액 초과 차단 |
| 거래처 반품 | 수령한 개수 중 실제 반품 수량을 기록. 발주 당시 포장 용량만큼 재고 차감, 발주 단가만큼 매입 정산액 감소 |
| 분할 지급·환급 → 거래처 환급 수령 | 취소·반품으로 발생한 초과 지급액을 실제 돌려받은 후 기록 |
| 분할 지급·환급 → 입력 정정 | 잘못 입력한 지급·환급 항목을 선택해 반대 금액의 정정 이력을 추가. 원 기록 보존 |

정산 금액, 순지급액, 남은 지급액 또는 돌려받을 금액을 별도로 표시합니다. 분할 지급 후에는 발주 전체 취소로 지급 이력을 숨길 수 없습니다. 미입고 잔량을 취소하고 환급 수령을 기록하세요. 발주에 연결된 반품만 지원하며 세금계산서, 운송비·반품 수수료, 계좌이체 API는 포함하지 않습니다.

입고 수량을 정정하는 ‘입고 취소’와 실제 거래처에 물건을 보내는 ‘반품’을 구분합니다. 반품 이력이 있는 품목의 기존 입고 취소는 막고, 재고보다 많은 반품도 차단합니다. 반품과 잔량 취소는 입력 전에 실제 수량을 확인하세요.

## 계정 복구

1. 원장 재인증 → **설정 · 백업 → 백업 · 이전 자료 → 원장 계정 복구**에서 코드를 발급합니다.
2. 코드 파일을 원장만 접근할 수 있는 별도 장소에 보관합니다. 서버에는 코드 원문을 저장하지 않습니다.
3. 로그인 화면 **아이디·비밀번호 찾기**에서 코드와 새 비밀번호(12~128자)를 입력합니다. 올바른 코드 확인 후 원장 아이디를 표시합니다.
4. 사용한 코드는 폐기하고 해당 원장의 모든 기존 로그인을 종료합니다. 로그인 후 새 복구 코드를 발급하세요.

새 코드 발급, 비밀번호 변경 또는 백업 복원 후 이전 코드는 사용할 수 없습니다. 비활성·퇴사·권한이 변경된 원장의 코드는 복구에 사용할 수 없습니다. 직원은 원장에게 초기화를 요청합니다. 미리 발급한 코드가 없으면 서버 운영자 복구 도구를 계속 사용합니다. 공개 화면에서 임의로 `admin/admin`을 설정하는 기능은 제공하지 않습니다.

## 자동 백업

- `start.bat`과 `npm start`로 서버 실행 시 기본 활성화. 준비된 DB가 있으면 시작 약 10초 후 확인하고 이후 최대 1시간 간격으로 점검합니다. 마지막 성공으로부터 24시간 이상 지나면 백업합니다.
- 기본 위치는 DB 파일 옆 `backups` 폴더, 최근 자동 백업 14개를 보관합니다. 수동 백업은 삭제하지 않습니다.
- SQLite 백업 API로 일관된 스냅샷을 만들고 무결성을 확인합니다. 실패 상태는 **설정 · 백업 → 백업 · 이전 자료 → 자동 백업 상태**와 서버 로그에 표시됩니다. ‘지금 서버에 백업’으로 재시도할 수 있습니다.
- `AUTO_BACKUP=0`으로 비활성화, `BACKUP_DIR`로 서버의 보호된 디렉터리를 지정할 수 있습니다. Docker 기본 경로는 `/app/data/backups`로 영구 볼륨에 저장합니다.
- 서버가 꺼져 있으면 실행되지 않으며 자동 외부 업로드·이메일 알림은 없습니다. PC·디스크 고장에 대비하려면 다운로드한 백업을 접근이 제한된 별도 저장소에도 보관해야 합니다.

## 저장 구조와 API

DB는 기존 9개 테이블에 `recovery_codes(token_hash,user_id,password_tag,created_at)`를 추가하여 총 10개이며 SQLite `user_version`은 4입니다. 기존 업무 JSON의 `schemaVersion:2`는 유지합니다. 발주 취소·반품·지급 이벤트는 `purchase_orders.changes`에 저장하고 원 발주 수량·단가는 보존합니다.

새 업무 요청은 기존 버전 충돌 검사·CSRF·권한·요청 ID 중복 방지를 공통 적용합니다.

- `POST /api/actions/payment.reprice`
- `POST /api/actions/payment.refund`: 시술 항목에 `amount` 입력 지원
- `POST /api/actions/payment.create`: `materialUsage`, `materialReason` 지원
- `POST /api/actions/purchase.closeRemaining`, `purchase.return`, `purchase.settlement`
- `GET/POST /api/admin/recovery`: 원장 재인증 필요
- `POST /api/auth/recover`: 일회용 코드 필요, 시도 횟수 제한
- `GET /api/admin/backup-status`, `POST /api/admin/backup-run`: 원장 재인증 필요
