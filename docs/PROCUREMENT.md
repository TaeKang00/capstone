# 발주 · 입고 · 용량 재고 — 교수님 피드백 반영

2026-10-12 기준. 한 매장 내부 ERP의 수동 발주·입고 흐름입니다. 거래처에 주문을 자동 전송하거나 은행 이체를 실행하지는 않습니다.

## 요구사항과 구현 위치

| 요구사항 | 화면 / 동작 |
|---|---|
| 로그인 후 프로그램 실행 | `start.bat` 실행 → 로그인 → 오늘의 매장. 새 로컬 설치의 시연 계정은 `admin / admin` |
| 거래처 등록·목록·사용/미사용 | **발주 · 거래처 → 거래처**. 담당자·연락처·메모 입력, 사용 상태별 조회 |
| 추가 가능한 분류 테이블 | **발주 · 거래처 → 품목 분류**. 실제 SQLite `item_categories` 테이블에 저장 |
| 품목 분류별 조회 | **재고 · 입고 → 품목 분류별 조회**. 기본 분류: 시술 제품·관리 제품·판매 제품 |
| 품목 사용/미사용 | **재고 · 입고 → 품목 수정**. 사용 중인 시술 재료는 연결을 해제한 뒤 미사용으로 전환 |
| 개수 입고 → 용량 관리 | 품목의 관리 단위 `ml`/`g`와 `1개당 용량` 지정. 수령 개수 × 발주 당시 포장 용량을 재고에 더함 |
| 간편 발주 | **발주 내역 → 발주 등록**. 거래처 선택 → 사용 품목 체크 → 수량·개당 금액 변경 → 합계 확인 |
| 발주 목록 항목 | 발주일·거래처·품목·발주 수량·입고 수량·제품 총 금액·납품 예정일·배송 상태·지급 여부·조회 금액 합계 |
| 배송 상태별 조회 | 대기·배송중·배송완료·취소. 품목별 상태로 조회하며 부분 입고 품목은 대기 |
| 일부 수량 입고 | 상세에서 이번에 실제 받은 개수만 입력. 100개 중 50개 입고 → 대기·부분 입고·잔량 50개 |
| 발주 완료 | 모든 품목의 발주 수량을 수령하면 자동 배송완료. 상태만 바꿔 재고를 늘리는 기능은 없음 |
| 대금 지급 확인 | 입고 상태와 별도로 전액 지급/미지급 기록, 실제 지급일·참조번호·사유 보관 |
| 시술 사용량 차감 | 원장 관리의 시술별 1회 재료 소모량 설정. 해당 시술 수납 기록 시 총 용량에서 차감 |

분류는 검색·관리용 묶음이며 **시술 재료 / 판매 상품**은 재고의 용도입니다. 예를 들어 `관리 제품` 분류의 트리트먼트를 `시술 재료`로 사용할 수 있습니다.

## 발표용 한 바퀴 시연 (약 5분)

1. `admin / admin`으로 로그인합니다. 기존 계정은 자동으로 변경되지 않습니다. 시연 계정으로 전환할 때만 서버 종료 후 `npm run setup:demo`를 실행합니다.
2. 발주 · 거래처에서 `봄 유통`을 등록합니다. 분류에 `두피 케어`를 추가합니다.
3. 재고 · 입고에서 `케어 샴푸`를 등록합니다. 분류 두피 케어, 용도 시술 재료, 단위 ml, 1개당 용량 500, 입고 단가 20,000원, 보충 기준 500ml, 거래처 봄 유통으로 지정합니다.
4. **시술 · 재료 설정**으로 이동해 원장 재인증을 합니다. `두피 케어 시술` 30,000원·30분을 등록하고 케어 샴푸 100ml를 1회 소모 재료로 연결합니다.
5. 발주 등록에서 봄 유통 선택 → 케어 샴푸 체크 → 3개 선택. 총 금액은 60,000원이며 아직 재고는 0ml입니다.
6. 발주 상세에서 배송 시작을 기록합니다. ‘배송중’ 필터로 조회할 수 있습니다.
7. 입고 수량 입력에서 1개를 등록합니다. 재고는 500ml, 상태는 ‘대기 · 부분 입고’, 미입고는 2개입니다.
8. 나머지 2개를 입고합니다. 총 1,500ml이며 자동으로 배송완료가 됩니다.
9. 실제 거래처에 60,000원을 지급했다고 가정한 시연 기록을 남깁니다. 지급 완료 필터로 조회합니다. 실제 이체는 ERP 밖에서 처리합니다.
10. 수납 · 환불에서 두피 케어 시술을 선택하고 외부 단말기 결과를 기록합니다. 시술 1회 사용량 100ml가 차감되어 재고는 1,400ml가 됩니다.
11. 재고 변동 이력에서 +500ml, +1,000ml, -100ml를 확인합니다.

시연에는 가상 거래를 사용하세요. 운영 DB에 테스트 입고·수납·지급 기록을 남기지 않습니다.

## 상태와 정정 규칙

- 발주 자체는 재고를 변경하지 않습니다. 수령한 품목과 수량을 직원이 입력합니다.
- 배송 상태는 품목별로 계산합니다. 2품목 중 한 품목만 전량 입고되면 그 품목은 배송완료, 나머지는 대기/배송중입니다. 발주 전체는 모든 품목 입고 시 완료됩니다.
- 부분 입고된 품목은 배송 시작 기록이 있더라도 ‘대기’로 표시합니다. 잔량과 부분 입고 문구를 함께 보여 줍니다.
- 발주 당시 품목명·단위·1개당 용량·입고 단가를 별도로 보관합니다. 이후 상품의 포장 용량이나 단가가 바뀌어도 기존 발주가 달라지지 않습니다.
- 발주에 연결된 입고는 발주 상세에서 **이 입고 취소 → 올바른 수량으로 다시 입고**합니다. 재고 화면에서 직접 정정해서 발주 잔량과 불일치하지 않도록 제한합니다.
- 입고를 취소해 재고가 음수가 된다면 취소하지 않습니다. 이미 사용한 재고를 확인해야 합니다.
- 입고 또는 지급 기록이 있는 발주는 바로 취소할 수 없습니다. 기록을 먼저 확인·정정합니다. 취소 사유와 처리자는 이력에 남습니다.
- 미사용 거래처·품목으로 새 발주를 만들 수 없습니다. 이미 등록한 발주의 수령 및 지급 기록은 계속 처리할 수 있습니다.
- 대금 지급은 발주 금액 **전액 지급 여부**입니다. 분할 지급·외상 잔액 장부·매입 세금계산서·반품 정산은 이번 범위에 포함되지 않습니다.
- 기존 직접 입고도 계속 지원합니다. 같은 물건을 직접 입고와 발주 입고 양쪽에 중복 기록하지 않습니다.
- ml·g는 소수점 셋째 자리까지, 포장 개수는 정수로 입력합니다. 품목당 현재 포장 용량 하나를 설정하며 용량 옵션별 재고를 별도 보관하는 기능은 아닙니다.

| 원장·매니저 | 거래처·분류·품목 관리, 발주 등록·배송·입고·취소·지급 기록 |
| 접수 직원 | 목록 조회, 실제 입고 기록, 입고 취소. 발주 금액·거래처·지급 상태 변경 불가 |

급여·직원 계정·시술 설정 등 기존 보호 영역의 원장 재인증은 유지됩니다.

## 실제 DB 구조 (전체 9개 테이블)

기존 `users`, `sessions`, `app_state`, `audit`, `requests`에 다음 4개 테이블을 추가했습니다.

| 테이블 | 주요 컬럼 | 관계 |
|---|---|---|
| item_categories | id, name, active | 품목의 categoryId와 논리적으로 연결 |
| suppliers | id, name, contact, phone, note, active | purchase_orders.supplier_id의 실제 참조 대상 |
| purchase_orders | id, supplier_id, supplier_name, date, delivery_date, shipped, cancelled, paid, paid_date, reference, notes, created_at, actor_name, changes | 거래처 1:N 발주 |
| purchase_order_lines | id, order_id, item_id, item_name, unit, pack_size, quantity, unit_cost | 발주 1:N 상세. UNIQUE(order_id,item_id) |

`purchase_orders.supplier_id`와 `purchase_order_lines.order_id`는 SQLite 외래키입니다. 고객·예약·재고 품목·입고·급여 등 기존 업무 데이터는 여전히 `app_state.data` JSON에 있으며 `item_id`·`categoryId`의 존재 검증은 서버에서 수행합니다. 전체 DB 정규화를 완료한 것은 아닙니다.

- 입고 JSON에는 `orderId`, `orderLineId`, `packSize`, `packQty`를 추가해 어느 발주에서 받은 수량인지 연결합니다.
- 입고 합계에서 취소된 기록을 제외해 잔량과 배송 상태를 계산합니다. 완료 상태를 수량과 따로 수정하지 않습니다.
- API 응답에는 기존 화면 구조와 연결하도록 테이블 데이터를 합쳐 반환합니다. 신규 네 가지 엔티티를 app_state JSON에 중복 저장하지 않습니다.
- 기존 파일을 열면 테이블과 기본 분류를 추가하고 DB 버전을 3으로 올립니다. 기존 재고 수량은 자동 환산하지 않습니다. 기존 품목은 포장 용량 미설정 시 1 관리 단위로 취급합니다.
- DB 백업 파일에는 새 테이블도 함께 포함됩니다. 운영 파일 업데이트 전 백업을 보관하고 단일 서버로 실행하세요.

## API와 검증

공통 `POST /api/actions/:type`에 `{payload, version, requestId}` 형식으로 요청합니다.

| type | 목적 |
|---|---|
| supplier.save | 거래처 등록·수정·사용 상태 |
| category.save | 분류 등록·수정·사용 상태 |
| purchase.create | 발주와 선택 품목 등록 |
| purchase.ship | 배송 시작 기록 |
| purchase.receive | 여러 품목의 실제 수령 개수 입력 |
| purchase.receiptCancel | 발주에 연결된 입고 취소 |
| purchase.payment | 대금 전액 지급 여부 기록·정정 |
| purchase.cancel | 미입고·미지급 발주 취소 |
| inventory.item | 분류·거래처·포장 용량·입고 단가 포함 품목 저장 |
| inventory.receipt | 직접 입고. packQty 입력 시 포장 개수를 총 용량으로 환산 |

기존 인증·CSRF·버전 충돌·중복 요청 방지와 동일한 규칙을 적용합니다. 발주, 입고, 재고, 작업 이력, 요청 기록을 한 트랜잭션에서 저장하므로 중간 검증 실패 시 일부만 반영되지 않습니다.

검증 시나리오: 전체 거래 순환, 100개 중 50개 부분 입고, 초과/중복 입고 거절, 용량 스냅샷 보존, 소비 후 입고 취소 제한, 미사용 거래처, 권한 위조 거절, SQLite 테이블 영속화, 모바일 입력과 실패 후 재시도.
