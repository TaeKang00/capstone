# Salon ERP production candidate implementation contract

Target: single salon internal ERP; external payment-terminal results recorded, not card approval integration. Korean UI. Node 24+, node:sqlite, Express, React18 + Vite. No prototype demo people/data on fresh install.

## Business state (server-owned)
`{schemaVersion:2, store, staff:[], services:[], customers:[], appointments:[], transactions:[], refunds:[], items:[], receipts:[], logs:[], inventoryOperations:[], payroll:[], seq:{}}`.
IDs opaque strings. Money KRW nonnegative safe integer. Dates YYYY-MM-DD Asia/Seoul. Appointment minutes from midnight. Timestamps ISO.
This is the stored business state, not a response every session may read. Shared, work, owner-private and personal-private responses use different projections (see HTTP contract).
- store: `{name,phone,address,timeZone:'Asia/Seoul',open:600,close:1200,slotMinutes:30,closedWeekdays:[]}`
- staff: `{id,name,role:'owner'|'manager'|'designer'|'reception',phone,status:'active'|'inactive',workingDays:[0,1,2,3,4,5,6],startMinutes:600,endMinutes:1200,breakStart:null,breakEnd:null}`. User's staffId references this. Staff role for operations must match linked user role; account management handles syncing.
- services: `{id,name,price,duration,materials:[{itemId,quantity}],active:true}`
- customers: `{id,name,phone,memo,warning,createdAt,archived:false}`
- appointments: `{id,date,start,duration,customerId:null,guestName:'',guestPhone:'',staffId,serviceIds:[],notes:'',status:'booked'|'checked_in'|'in_service'|'completed'|'cancelled'|'no_show',transactionId:null,changes:[]}`
- items: existing inventory shape `{id,name,kind:'시술 재료'|'판매 상품',unit:'g'|'ml'|'개',qty,min,price,active:true}`
- receipts/logs/inventoryOperations: use existing `src/inventory.js` API, server ctx actual authenticated actor.
- transactions: `{id,appointmentId:null,customerId:null,customerName,staffId,serviceDate,date,time,lines:[{id,type:'service'|'product',refId,name,unitPrice,quantity,discount,total}],discount,subtotal,total,method:'card'|'cash'|'transfer',reference:'',notes:'',status:'paid'|'partially_refunded'|'refunded',actorId,createdAt,changes:[]}`. lines.discount proportional allocation of transaction discount; lines.total net.
- refunds: `{id,transactionId,date,time,lines:[{lineId,quantity,amount,restock}],amount,method,reference,reason,actorId,createdAt}`. Original transactions and service-consumption logs preserved. Daily settlement uses event date, not original sale date.

## Domain module ownership/export
`server/operations.cjs`: exports `initialState({storeName,ownerName,ownerStaffId}), applyOperation(data,type,payload,ctx)`.
`server/commerce.cjs`: exports `applyCommerce(data,type,payload,ctx), getReport(data,{from,to,staffId?})`.
Each mutation returns NEW state, no database I/O. Throw Error with `status` (400/403/409/422), `code` and message for user. Unknown type throws status400. Server routes based action prefix whitelist, module handles payload constraints and actor ownership. ctx `{actor:{id,name,role,staffId},today:'YYYY-MM-DD',now:'ISO',requestId}`. Reject invalid IDs, amounts, dates, enum values, length; do not trust client snapshots/actor.

Actions (POST /api/actions/:type) body `{payload,version,requestId}` -> `{data,version,session?}`. Strict exact global version compare within DB BEGIN IMMEDIATE; conflict409 before mutation; idempotent actorId+requestId stores a signature and version marker. A retry revalidates current authorization and returns current state projected for that authorization, never a previously privileged response snapshot. Client preserves draft on conflict, refreshes state and asks recheck/retry. Same requestId cannot run different payload.
Operations: `customer.save` payload `{id?,name,phone,memo,warning}`; `customer.archive` `{id,archived}`; `appointment.save` `{id?,date,start,duration?,customerId?,guestName?,guestPhone?,staffId,serviceIds,notes}`; `appointment.status` `{id,status,reason?}` (reversal audited; cannot bypass recorded payment); `staff.save` `{id?,name,phone,role,status,workingDays,startMinutes,endMinutes,breakStart,breakEnd}`; `service.save` `{id?,name,price,duration,materials,active}`; `store.save` store fields; `legacy.import` `{data:legacyV2}` (owner only, empty business data only, validate all and preserve stock exactly, no partial import).
Commerce: `payment.create` `{appointmentId?,customerId?,guestName?,staffId,serviceDate?,lines:[{type,refId,quantity,unitPrice?}],discount,method,reference,notes}`; `payment.correct` `{id,staffId?,method?,reference?,reason}` metadata-only, NEVER consumes stock again; amount/line corrections use explicit refund/new extra sale. `payment.refund` `{transactionId,lines:[{lineId,quantity,restock}],method,reference,reason}` amount server calculates remaining quantities+discount; no overrefund, service use stays consumed, products restock only selected quantities. `inventory.receipt` existing `{itemId,qty,date,memo}`; `inventory.correct` `{receiptId,qty,reason,expectedRevision}`; `inventory.cancel` `{receiptId,reason,expectedRevision}`; `inventory.threshold` `{itemId,qty}`; `inventory.adjust` `{itemId,qty,reason}`; `inventory.item` `{id?,name,kind,unit,min,price,active}` creating qty0, receipt/adjust only for qty. `getReport` -> `{from,to,gross,refunds,net,count,byMethod:[{method,gross,refunds,net}],byStaff:[{staffId,name,total,count}],daily:[{date,gross,refunds,net}],transactions,refundEntries}`.

## HTTP and access contract
- GET /api/health -> {status:'ok'}
- GET /api/bootstrap -> {needsSetup:boolean,setupAllowed:boolean,requiresToken:boolean}
- POST /api/bootstrap {storeName,name,email,password,setupToken?} -> session object; only empty DB; production requires configured BOOTSTRAP_TOKEN; dev loopback initial setup only.
- GET /api/auth/me -> `{user:{id,name,email,role,staffId,mustChangePassword},csrfToken,mode:'work'|'shared',idleExpiresAt}` or401. Shared sessions return the synthetic shared user, not the account that previously worked on that PC.
- POST /api/auth/login `{email,password}` -> work session object for the actual operator. POST /api/auth/logout ->204; POST /api/auth/password `{currentPassword,newPassword}` -> work session object (rotate session, revoke others).
- POST /api/auth/lock -> shared session object and revokes private grants. POST /api/auth/activity -> current work session with refreshed 5-minute idle deadline; only deliberate user interaction should trigger this, not polling.
- POST /api/auth/private/unlock `{scope:'owner'|'personal',email,password}` -> `{accessToken,scope,user,expiresAt,idleExpiresAt}`. Owner scope requires an active owner account and can open from a shared session without changing the work identity. Personal scope requires the currently signed-in work user and cannot select another staff member. Temporary passwords must be changed before opening protected areas.
- POST /api/auth/private/lock ->204 (idempotent grant revocation). POST /api/auth/private/activity with `X-Private-Token` -> `{scope,expiresAt,idleExpiresAt}`; refreshes the 3-minute idle deadline without extending the 10-minute absolute deadline.
- GET /api/state -> `{data,version,session}`. Shared projection contains store details, staff names/schedules, public service names and today's appointments with masked customer data; other business arrays are empty. Work projection excludes all payroll, private staff fields, account records, audit logs and legacy archive. Designer transactions/refunds and appointments are further filtered to own staffId. Password hashes/users/sessions are never part of business state responses.
- GET /api/admin/state with owner `X-Private-Token` -> `{data,version}` including privileged business state, excluding the legacy archive.
- GET /api/personal/state with personal `X-Private-Token` -> `{data,version}` containing only public store details, own public staff data, and own finalized/paid payslips. Other customers, transactions and private business arrays remain empty.
- POST /api/actions/:type as above; CSRF via `X-CSRF-Token`, credentials same-origin. `staff.save`, `service.save`, `store.save`, `legacy.import` and all `payroll.*` actions require owner private scope. Other actions require an active work session and that role's operational permissions. The authenticated actor is recorded separately from the service-provider staffId.
- GET /api/reports?from=&to=&staffId= -> report; owner private scope required.
- GET /api/users -> `{users:public users[]}`; POST /api/users `{name,email,role,staffId,password}` creates account for existing staff; PATCH /api/users/:id `{active?,role?,password?}` changes it. All require owner private scope, including account reads. Privilege and last-owner checks remain; admin reset sets mustChangePassword; changes revoke sessions and private access. Password change required blocks other business APIs.
- GET /api/audit?limit= -> `{entries:[{id,at,actorName,action,summary}]}`; owner private scope required.
- GET /api/export?from=&to= -> CSV with safe formula escaping; owner private scope required. Client downloads through authenticated fetch so the private token is sent in a header, never the URL.
- GET /api/backup -> DB snapshot download; owner private scope required and rechecked after snapshot generation.
JSON errors `{error:{code,message,fields?,session?}}` have meaningful statuses. Locked work actions return423 `WORK_LOCKED`; missing/expired private access returns403 `PRIVATE_AUTH_REQUIRED`/`PRIVATE_SESSION_EXPIRED`. Failed private credentials do not log out the work session. Request size is limited; sessions use HttpOnly SameSite cookies and Secure in production; CSRF and Origin are validated. Passwords use scrypt with random salt. Authentication is rate-limited. SQLite stores transactional state, audit and idempotency markers.

Work role permissions: owner and manager may perform customer/appointment/payment/inventory actions, including item registration. Reception may perform customer/appointment/payment/inventory actions except inventory.item. Designer may perform only customer.save and own appointment.save/status (server checks staffId), read stock/services and own payments; no payment or inventory mutations. None of these work roles may use privileged staff, account, settings, report, backup or payroll endpoints without a separately verified owner grant. Server checks are authoritative; hidden menus are not authorization.

Payroll access: only a separately verified owner grant manages all payroll. Every role's ordinary work response excludes payroll. Personal access requires the current operator's own password and permits only their finalized/paid payslips; manager is subject to the same personal-only restriction. Personal access cannot mutate payroll.

Work inactivity locks after 5 minutes. Private access locks after 3 minutes without interaction, at most 10 minutes after issue, and immediately in the UI when the protected document becomes hidden or the user locks/leaves it. Background refresh does not keep either session active. Private tokens are random, session-bound, hashed in an in-memory server grant map and never persisted in browser storage. Account/role/password/active status and deadlines are rechecked on every privileged request. Late responses are discarded after a lock or identity change. Server restart invalidates private grants.

OS boundary: app authentication cannot protect SQLite files, backups or `scripts/reset-owner.cjs` from someone with server filesystem permissions. Production uses an app/DB server inaccessible to staff at the OS level and browser-only HTTPS clients on shared PCs. SQLite stays on the server's local disk; restrict server, Docker, backup and recovery access to designated operators.

## React contract (root owns App/API/ui + Staff/Settings; page agents consume)
Root supplies `src/api.js`: api(path, options={}) fetches the /api path (`path` starts '/state', '/auth/me' etc), parses JSON/errors and rejects stale responses. `getSession`, `setSession`, `getPrivateAccess`, `setPrivateAccess` use memory only; CSRF is automatic. Private calls accept `options.privateAccess` and send `X-Private-Token`. `download(path,filename,options)` uses the same authorization and stale-response protection for CSV and backups. `src/components/ui.jsx` exports `Button`, `Modal`, `Field`, `Badge`, `EmptyState`, `Money`, `ConfirmDialog`.
All pages default export function `Page({data,user,version,runAction,refresh,notify,navigate})`. `runAction(type,payload,requestId?)` Promise -> returned state envelope, sets root data/version; on conflict refresh state and throw error while preserving local dialog; duplicate double-click disabled in page. A given unchanged attempt retry should reuse requestId; root runAction generates per call unless passed, UI retain same requestId on network failure; root API can maintain signature-based pending IDs. `navigate('appointments'|'customers'|'payments'|'inventory'|'sales'|'staff'|'settings'|'dashboard', {customerId?,appointmentId?,transactionId?})` updates `routeContext` passed to pages as prop.
Page components: `src/pages/Appointments.jsx`, `Customers.jsx`, `Payments.jsx`, `Inventory.jsx`, `Dashboard.jsx` are work pages. `SharedDesk` renders the sanitized public desk, `AccessGate` handles operator/owner/personal authentication, and `PrivateWorkspace` isolates Staff/Payroll/Sales/Settings from work state and clears protected content on lock. Personal workspace renders Payroll with `personalOnly` and permits reading/printing only. Navigation between work and private areas is an authentication boundary, not merely a role-based menu switch.
Shared style classes: page-header,page-title,page-description,page-actions,btn,btn-primary,btn-secondary,btn-danger,btn-ghost,card,card-header,card-body,grid,grid-2,grid-3,stat-grid,stat-card,toolbar,field,field-label,input,textarea,select,help,error,alert,alert-warning,alert-success,badge,badge-success,badge-warning,badge-danger,badge-muted,table-wrap,table,empty-state,muted,stack,row,amount,tabs,tab,active. root owns global src/styles.css. Pages may add their own src/pages/<Name>.css if needed, import themselves, avoid overwriting global.
UI date helpers local Intl Asia/Seoul, not UTC split now. Customer warning prominently in appointment/payment. Mobile sidebar drawer, mobile cards for lists. Persistent labels, dirty modal guard, keyboard focus trap, loading/empty/error, no browser alert/prompt/confirm for business actions. Known partial refund & metadata-only corrections explicit UI.
